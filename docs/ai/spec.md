# Inventory API - Specification

Status: approved before implementation.

This document is the contract that was written before any production code was generated. It defines the scope, the data model, the HTTP contract, the business rules and the acceptance criteria. Implementation was validated against this document, and every deviation is recorded in `docs/ai/decisions.md`.

## 1. Goal

Build a RESTful API that manages products, categories and inventory movements. The API must be protected with OAuth2, persist data in SQL Server, use Entity Framework Core for reads and Dapper for writes, apply CQRS, and run with a single `docker compose up --build` command.

The deliverable is a public repository containing the source code, the Docker assets, the automated tests and the documentation required by the exercise.

## 2. Scope

### In scope

- CRUD for products.
- CRUD for categories.
- Registration of `In` and `Out` inventory movements.
- Read model for products, categories and movement history.
- OAuth2 protection for every endpoint except the health check.
- SQL Server schema created and versioned with EF Core migrations.
- Seed data that makes the API usable immediately after startup.
- Unit tests for domain rules, handlers and validators.
- Swagger UI with the OAuth2 authorization code flow.
- Docker Compose stack with API, SQL Server and Keycloak.
- README with setup, run, debug and test instructions.
- Documentation of the AI-assisted process and the decision-making answers.

### Out of scope

- Frontend or mobile client.
- Multi-warehouse inventory.
- Purchase orders, suppliers, customers or billing.
- Role-based authorization policies beyond requiring an authenticated principal.
- Event sourcing, message brokers or a physically separated read database.
- Production hardening of Keycloak or SQL Server.
- Integration tests against a real database container.

## 3. Actors

| Actor | Description |
|---|---|
| API consumer | Machine client using the OAuth2 client credentials flow |
| Swagger user | Human using the authorization code flow with PKCE |
| Operator | Person running the Docker Compose stack |

## 4. Domain model

### Category

| Field | Type | Rules |
|---|---|---|
| Id | guid | Primary key, generated by the API |
| Name | string(120) | Required, unique, trimmed |
| Description | string(500), nullable | Optional, trimmed |
| IsActive | bool | Defaults to `true` |
| CreatedAt | datetime2 (UTC) | Set on creation |
| UpdatedAt | datetime2 (UTC) | Set on creation and on every update |

### Product

| Field | Type | Rules |
|---|---|---|
| Id | guid | Primary key, generated by the API |
| Sku | string(40) | Required, unique, normalized to upper case |
| Name | string(200) | Required, trimmed |
| Description | string(1000), nullable | Optional, trimmed |
| CategoryId | guid | Required, must reference an existing active category |
| Price | decimal(18,2) | Greater than zero |
| Stock | int | Read-only through the API, starts at `0` |
| MinimumStock | int | Greater than or equal to zero |
| IsActive | bool | Defaults to `true` |
| CreatedAt | datetime2 (UTC) | Set on creation |
| UpdatedAt | datetime2 (UTC) | Set on creation and on every update |

### InventoryMovement

| Field | Type | Rules |
|---|---|---|
| Id | guid | Primary key, generated by the API |
| ProductId | guid | Required, must reference an existing active product |
| Type | enum | `In = 1`, `Out = 2` |
| Quantity | int | Greater than zero |
| UnitCost | decimal(18,2) | Greater than or equal to zero |
| Reason | string(500), nullable | Optional, trimmed |
| Reference | string(100), nullable | Optional, trimmed |
| CreatedBy | string(100) | Taken from the access token, never from the request body |
| CreatedAt | datetime2 (UTC) | Set by the API |

### Relationships

- A category has many products.
- A product belongs to one category.
- A product has many inventory movements.
- Deleting a category or a product is a soft delete (`IsActive = false`).
- Foreign keys use `ON DELETE RESTRICT` so audit rows are never orphaned.

## 5. Business rules

1. A new product always starts with `Stock = 0`.
2. `Stock` cannot be modified through the product create or update endpoints.
3. `Stock` only changes when an inventory movement is registered.
4. An `In` movement increments stock by `Quantity`.
5. An `Out` movement decrements stock by `Quantity`.
6. An `Out` movement that would produce negative stock is rejected with `409 Conflict`.
7. A movement cannot be registered for a missing or inactive product (`404 Not Found`).
8. A product cannot reference a missing or inactive category (`404 Not Found`).
9. SKU and category name are unique across active and inactive rows, because the database constraint is global.
10. A category with at least one active product cannot be deleted (`409 Conflict`).
11. Deactivated products and categories are excluded from default reads.
12. Inventory movements are immutable; there is no update or delete endpoint.
13. The stock update and the movement insert happen in the same transaction.
14. The product row is read with `UPDLOCK, ROWLOCK` before the stock calculation.

## 6. HTTP contract

Base path: `/api`. All routes except `/health` require `Authorization: Bearer <token>`.

### 6.1 Products

#### List products

```http
GET /api/products?categoryId={guid}&search={text}&isActive={bool}&page={int}&pageSize={int}
```

| Parameter | Required | Default | Rules |
|---|---|---|---|
| categoryId | No | null | Filters by category |
| search | No | null | Case-insensitive match on name or SKU |
| isActive | No | null | When omitted, returns active and inactive rows |
| page | No | 1 | Values below 1 are normalized to 1 |
| pageSize | No | 10 | Omitted or non-positive values use 10; values above 100 are capped at 100 |

Response `200 OK`:

```json
{
  "items": [
    {
      "id": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
      "sku": "LAP-001",
      "name": "Laptop 14",
      "description": "14 inch laptop",
      "categoryId": "8a1f0f5e-2f4e-4a4c-9d3c-6f0a1f6a9b10",
      "categoryName": "Electronics",
      "price": 1200.00,
      "stock": 25,
      "minimumStock": 5,
      "isActive": true,
      "createdAt": "2026-11-04T12:00:00Z",
      "updatedAt": "2026-11-04T12:00:00Z"
    }
  ],
  "page": 1,
  "pageSize": 10,
  "totalCount": 1,
  "totalPages": 1
}
```

#### Get product by id

```http
GET /api/products/{id}
```

- `200 OK` with a product.
- `404 Not Found` when the product does not exist.

#### Create product

```http
POST /api/products
Content-Type: application/json

{
  "sku": "LAP-001",
  "name": "Laptop 14",
  "description": "14 inch laptop",
  "categoryId": "8a1f0f5e-2f4e-4a4c-9d3c-6f0a1f6a9b10",
  "price": 1200.00,
  "minimumStock": 5
}
```

- `201 Created` with the new guid as the body and a `Location` header.
- `400 Bad Request` when validation fails.
- `404 Not Found` when the category does not exist or is inactive.
- `409 Conflict` when the SKU already exists.

#### Update product

```http
PUT /api/products/{id}
Content-Type: application/json

{
  "id": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
  "sku": "LAP-001",
  "name": "Laptop 14 Pro",
  "description": "14 inch laptop, 32 GB",
  "categoryId": "8a1f0f5e-2f4e-4a4c-9d3c-6f0a1f6a9b10",
  "price": 1350.00,
  "minimumStock": 4
}
```

- `204 No Content` on success.
- `400 Bad Request` when the route id and body id differ, or validation fails.
- `404 Not Found` when the product or the category does not exist.
- `409 Conflict` when the SKU belongs to another product.

#### Delete product

```http
DELETE /api/products/{id}
```

- `204 No Content` on success.
- `404 Not Found` when the product does not exist.

The operation sets `IsActive = false`. Movements are preserved.

### 6.2 Categories

#### List categories

```http
GET /api/categories?includeInactive={bool}
```

- `200 OK` with an array of categories.
- `includeInactive` defaults to `false`.

#### Get category by id

```http
GET /api/categories/{id}
```

- `200 OK` with a category.
- `404 Not Found` when the category does not exist.

#### Create category

```http
POST /api/categories
Content-Type: application/json

{
  "name": "Electronics",
  "description": "Devices and accessories"
}
```

- `201 Created` with the new guid as the body and a `Location` header.
- `400 Bad Request` when validation fails.
- `409 Conflict` when the name already exists.

#### Update category

```http
PUT /api/categories/{id}
Content-Type: application/json

{
  "id": "8a1f0f5e-2f4e-4a4c-9d3c-6f0a1f6a9b10",
  "name": "Electronics",
  "description": "Devices, accessories and components"
}
```

- `204 No Content` on success.
- `400 Bad Request` when the route id and body id differ, or validation fails.
- `404 Not Found` when the category does not exist.
- `409 Conflict` when the name belongs to another category.

#### Delete category

```http
DELETE /api/categories/{id}
```

- `204 No Content` on success.
- `404 Not Found` when the category does not exist.
- `409 Conflict` when the category still has active products.

### 6.3 Inventory movements

#### List movements

```http
GET /api/inventory-movements?productId={guid}&page={int}&pageSize={int}
```

- `200 OK` with a paged result ordered by `CreatedAt` descending.
- Pagination follows the same normalization rules as products.

#### Register movement

```http
POST /api/inventory-movements
Content-Type: application/json

{
  "productId": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
  "type": "Out",
  "quantity": 3,
  "unitCost": 32.50,
  "reason": "Customer order",
  "reference": "ORD-1001"
}
```

`type` accepts `In` or `Out` (case-insensitive because of the string enum converter).

- `201 Created` with the movement guid. The `Location` header points to the product movement history.
- `400 Bad Request` when validation fails.
- `404 Not Found` when the product does not exist or is inactive.
- `409 Conflict` when the movement would leave negative stock.

`CreatedBy` is resolved from the `preferred_username` claim, then from `HttpContext.User.Identity.Name`, then from the literal `unknown`.

### 6.4 Health

```http
GET /health
```

Response `200 OK`:

```json
{
  "status": "Healthy"
}
```

No authentication is required so containers and orchestrators can probe the process.

## 7. Error contract

All errors use RFC 7807 `ProblemDetails` with `Content-Type: application/problem+json`.

```json
{
  "type": "https://httpstatuses.com/409",
  "title": "Conflict",
  "status": 409,
  "detail": "Requested quantity 50 exceeds available stock 25.",
  "traceId": "00-9c2b1f7a4d0e3a4b8f6c5d4e3a2b1c0d-1a2b3c4d5e6f7a8b-00"
}
```

Validation errors include an `errors` object keyed by property name. Controllers do not catch exceptions; a single middleware maps domain exceptions to status codes.

| Exception | Status |
|---|---|
| `NotFoundException` | 404 |
| `ConflictException` | 409 |
| `InsufficientStockException` | 409 |
| `ValidationException` (FluentValidation) | 400 |
| Any other exception | 500 |

## 8. Authentication

- OAuth2 / OpenID Connect provider: Keycloak 26, realm `inventory`.
- Machine client: `inventory-api`, confidential, client credentials, secret supplied by the environment.
- Swagger client: `inventory-swagger`, public, authorization code with PKCE.
- Audience: `inventory-api`, added with a protocol mapper to both clients.
- The API validates signature, issuer, audience and lifetime.
- Access tokens live 15 minutes.
- The realm, clients, mapper and demo user are imported from `docker/keycloak/realm-export.json`.

The API must expose the Swagger authorization flow so a reviewer can call protected endpoints without an external REST client.

## 9. Architecture

```text
Inventory.Api -> Inventory.Infrastructure -> Inventory.Application -> Inventory.Domain
```

- `Inventory.Domain` has no framework references.
- `Inventory.Application` defines repository interfaces and MediatR handlers.
- `Inventory.Infrastructure` implements persistence with EF Core and Dapper.
- `Inventory.Api` is the composition root.

CQRS rules:

- Every command has exactly one handler.
- Every query has exactly one handler.
- Handlers depend on interfaces, never on concrete infrastructure types.
- Validation runs in a MediatR pipeline behavior before the handler.
- Read repositories use `AsNoTracking` and projections.
- Write repositories use parameterized SQL.

## 10. Non-functional requirements

| Concern | Requirement |
|---|---|
| Runtime | .NET 10 LTS |
| Database | SQL Server 2022 |
| Containerization | API, SQL Server and Keycloak in one Compose file |
| Configuration | .NET configuration with environment variables taking precedence; local demo defaults in `appsettings.Development.json` |
| Errors | RFC 7807 for every failure |
| Logging | Built-in ASP.NET Core logging, no sensitive data |
| Time | UTC everywhere, injected `TimeProvider` in handlers |
| Pagination | Page size capped at 100 |
| Concurrency | Stock updates serialized per product row |
| Code style | English only, one class per file, no comments, no commented code, no blank lines except before `return` |
| Methods | At most 25 lines, at most one level of nesting |
| Parameters | Objects or interfaces instead of loose primitive groups |

## 12. Acceptance criteria

1. `docker compose up --build` starts SQL Server, Keycloak and the API without manual steps.
2. `/health` returns `200` without a token.
3. Any `/api` route returns `401` without a token.
4. A client credentials token grants access to every `/api` route.
5. Swagger UI can obtain a token with the authorization code flow.
6. Products and categories support create, read, update and soft delete.
7. An `In` movement increases stock and appears in the history.
8. An `Out` movement decreases stock and is rejected when stock is insufficient.
9. Validation failures return `400` with field-level messages.
10. Missing resources return `404`; conflicts return `409`.
11. Seed data is available on a fresh database.
12. `dotnet build`, `dotnet test` and the Clean Code script succeed.
13. The repository contains no production secrets; only the intentional demo credentials used by the local containers.
14. All code and comments are in English.

## 13. Open questions resolved before coding

| Question | Resolution |
|---|---|
| Is stock edited directly? | No. Movements are the only write path. |
| Hard or soft delete? | Soft delete, to preserve the audit trail. |
| Separate read database? | No. One database, separate read and write code paths. |
| MediatR or custom dispatcher? | MediatR, for pipeline behaviors and low ceremony. |
| Keycloak or a custom issuer? | Keycloak, to avoid a hand-rolled OAuth2 server. |
| Apply migrations at startup? | Yes, to keep the one-command promise for this exercise. |
| Return the created entity or its id? | The id, plus a `Location` header. |
